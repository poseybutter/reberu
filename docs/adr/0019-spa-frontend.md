# ADR-0019. 프론트엔드: 같은 출처의 SPA, 보안 경계에서 전체 새로고침

> 버전: v0.1.0\
> 수정일: 2026-11-05

- 상태: Accepted
- 영향: [architecture/frontend.md](../architecture/frontend.md), [architecture/api.md](../architecture/api.md) API-FMT-05·06, [architecture/security.md](../architecture/security.md) SEC-HDR-02, OQ-24

## 맥락

- reberu는 로그인한 사람만 쓰는 업무 도구다. 검색 노출과 첫 화면의 서버 렌더링은 거의 필요 없다.
- 3D 공간에서 걷고 실시간으로 주고받으려면 한 페이지를 오래 열어 두어야 한다. 어떤 방식을 골라도 "새로고침 없이 오래 열린 페이지"의 결함을 다뤄야 한다.
- 세션은 서버 세션 쿠키(`SameSite=Lax`)와 CSRF 쿠키로 다루고, CSP는 인라인 스크립트를 막는다(SEC-SESS-02·09, SEC-HDR-02).
- 복사해 쓰는 단체도 같은 방식으로 띄울 수 있어야 하고, 운영할 서버가 적을수록 좋다.
- 오래 열린 페이지의 가장 위험한 결함은 계정·팀이 바뀐 뒤 이전 데이터가 남아 보이는 것이다.

## 결정

- 화면은 React + TypeScript로 만들고 Vite로 빌드한 단일 페이지 앱(SPA)이다. 결과물은 정적 파일이다.
- 화면 파일은 API와 같은 출처에서 제공한다. CORS를 열지 않는다.
- 서버 데이터는 TanStack Query 캐시에만 두고, 서버를 정본으로 본다.
- 계정·조직·팀이 바뀌는 보안 경계에서는 화면 안에서 상태를 고쳐 넘기지 않고 페이지를 완전히 다시 불러온다.
- 3D(three.js, React Three Fiber)는 공간 모듈 화면의 지연 로딩 조각에만 넣는다.
- 운영 CSP에 Trusted Types를 켠다.
- 도입 시점은 v0.3이다. v0.1~v0.2는 API와 테스트로 검증한다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| Next.js 같은 서버 렌더링 프레임워크 | Node 서버가 하나 더 생겨 공격 면과 운영 부담이 늘고, 인증이 두 곳으로 나뉜다. 서버 렌더링의 인라인 스크립트는 매 요청 nonce를 요구해 지금 CSP와 맞추기 어렵다. 장점(검색 노출, 첫 화면 속도)을 쓸 곳이 없다 |
| 서버가 HTML을 그리는 방식(템플릿 + 조각 교체) | 업무 화면은 단순해지지만 3D 공간은 결국 오래 열린 페이지라 두 방식을 함께 운영해야 한다 |
| 화면을 다른 출처(별도 도메인)에 둠 | CORS와 쿠키 설정이 복잡해지고 CSRF 방어가 약해지기 쉽다 |
| 보안 경계에서도 화면 안 이동만 씀 | 캐시, 구독, 3D 자원 가운데 하나라도 비우지 못하면 다른 팀 데이터가 보인다. 빠짐없이 비웠는지 증명하기 어렵다 |

## 결과

- 좋아지는 점: 운영할 서버가 늘지 않는다. 데이터가 섞이는 결함을 구조로 막는다. CSP를 엄격하게 유지한다.
- 감수하는 점: 팀을 바꿀 때마다 페이지를 다시 불러오는 짧은 대기가 생긴다. 오래 열린 페이지의 결함(옛 데이터, 배포 판 불일치, 자원 누수)을 규칙과 화면 시험으로 막아야 한다([architecture/frontend.md](../architecture/frontend.md)).
- 후속 작업: 프론트엔드 의존성은 시작할 때 목록과 판을 보여 주고 승인을 받는다. 화면 파일을 Spring Boot가 제공할지 앞단 프록시가 제공할지는 배포 방식을 정할 때 고른다.
