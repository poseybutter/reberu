# ADR-0018. 세션 저장소: 해시로 저장하는 직접 구현

> 버전: v0.1.0\
> 수정일: 2026-11-05

- 상태: Accepted
- 영향: [architecture/security.md](../architecture/security.md) §7.1, [domain/model.md](../domain/model.md) `auth_session`, [docs/ai/backend.md](../ai/backend.md) §1, SEC-SESS-11~14

## 맥락

- 세션은 서버 저장소에 두고, 계정 ID로 찾아 즉시 끊을 수 있어야 한다(SEC-SESS-01, SEC-SESS-07).
- 세 DB에서 같게 동작해야 한다([ADR-0013](0013-shared-db-portable-sql.md)).
- Spring Session JDBC는 세션 ID 원문을 DB에 저장한다. DB 내용이 새어 나가면 로그인 중인 사람으로 행세할 수 있다.
- Spring Session JDBC는 세션 속성을 Java 직렬화로 저장한다. 직렬화된 값을 다시 읽는 과정은 역직렬화 공격의 통로가 될 수 있다.
- 보안을 가장 앞에 두는 것이 이 프로젝트의 원칙이다.

## 결정

- Spring Session의 세션 저장소 인터페이스와 쿠키 처리는 쓰고, 저장소 구현은 우리 JDBC 코드로 만든다.
- 세션 ID 원문은 쿠키에만 두고, DB에는 SHA-256 해시만 저장한다(SEC-SESS-12).
- 세션에는 정해진 열만 둔다. 임의 속성 저장과 Java 직렬화를 쓰지 않는다. Spring Security의 인증 정보는 요청마다 계정 ID로 다시 만든다(SEC-SESS-13).
- OIDC 로그인 진행 값(`state`, `nonce`, `code_verifier`, 돌아갈 주소)은 같은 행의 정해진 열에 두고 10분 뒤 무효로 한다(SEC-SESS-14).
- 동시 세션 상한(SEC-SESS-11)은 필수로 올린다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| Spring Session JDBC를 그대로 씀 | 세션 ID 원문 저장과 Java 직렬화를 피할 수 없다 |
| 서버 메모리 세션 | 서버를 다시 켜면 모두 로그아웃되고, 서버를 늘리면 세션을 나눠 가질 수 없다. 계정별 즉시 무효화도 어렵다 |
| Redis 세션 저장소 | 운영할 구성 요소가 하나 늘고, 원문 저장 문제는 같다 |
| 토큰 기반(JWT) 세션 | 즉시 무효화가 어렵다. SEC-SESS-01이 금지한다 |

## 결과

- 좋아지는 점: DB 내용이 새어 나가도 세션을 가로챌 수 없다. 역직렬화 공격 통로가 없다. 세션에 무엇이 들어가는지 열 단위로 정해져 있다.
- 감수하는 점: 저장소 구현(만들기, 찾기, 갱신, 지우기, 계정별 찾기, 만료 정리)을 직접 만들고 시험해야 한다. 보안 핵심 코드이므로 다음 시험을 v0.1 완료 조건에 넣는다: 해시만 저장됨, 원문으로는 DB에서 찾을 수 없음, 세션 ID 재발급 시 이전 행 삭제(SEC-SESS-03), 유휴·최대 수명 만료, 계정별 즉시 무효화, 동시 세션 상한, 로그인 진행 값의 10분 만료와 1회 사용.
- 후속 작업: Spring Session 핵심 라이브러리 추가는 구현 시작 때 따로 승인을 받는다.
