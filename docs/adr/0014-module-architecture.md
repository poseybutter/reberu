# ADR-0014. 모듈 구조: 단방향 의존, 이벤트 저장소, 시작 검증

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [architecture/modules.md](../architecture/modules.md), [docs/ai/backend.md](../ai/backend.md) §2

## 맥락

- reberu는 기능을 모듈로 켜고 끄고, 복사한 저장소가 업스트림을 고치지 않고 확장 모듈을 더한다([ADR-0002](0002-core-and-modules.md)).
- v0.5 이후 작업은 모듈을 더하기만 해야 한다(PRD-MVP-02). 이것이 지켜지려면 코드 수준에서 경계가 강제되어야 한다.
- 업무 완료 → EXP 지급처럼 한 기능의 변화가 다른 기능에 퍼진다. 직접 호출로 이으면 기능끼리 묶여 하나를 뺄 수 없다.
- 지원 DB가 셋이다([ADR-0013](0013-shared-db-portable-sql.md)).

## 결정

- 코드를 core, 고정 기능, 모듈 세 단위로 나누고 의존은 모듈 → 고정 기능 → core 한 방향만 허용한다.
- 단위 사이 반응은 도메인 이벤트로 한다. 이벤트는 원인과 같은 트랜잭션에서 이벤트 저장소에 기록하고, 커밋 뒤 구독자마다 따로 전달한다. 구독자는 멱등이다.
- 모듈은 정의 클래스 하나로 계약을 등록하고, 서버는 시작할 때 계약을 검증해 어긋나면 시작하지 않는다.
- 모듈 켜짐 확인은 진입점(API, 이벤트, 작업, 실시간, 알림, EXP)에서 core가 한다.
- 확장 모듈은 Spring Boot 자동 구성으로 등록한다.
- 경계는 아키텍처 테스트로 CI에서 확인한다. 도구(Spring Modulith 또는 ArchUnit과 직접 만든 이벤트 저장소)는 OQ-55에서 정한다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 기존 패키지 구조(auth, team, project, task, score, global) 유지 | 모듈과 고정 기능, core의 구분이 없어 켜고 끄는 단위와 의존 방향을 강제할 수 없다 |
| 기능 사이 직접 호출 | 업무가 EXP·퀘스트·실시간을 알아야 해 기능을 뺄 수 없다 |
| 메모리 안 이벤트(커밋 뒤 바로 전달)만 사용 | 서버가 죽으면 전달 전 이벤트를 잃는다. EXP 누락이 생긴다 |
| 별도 메시지 브로커(Kafka 등) | 서버 한 대 규모에서 운영 부담이 크다. 이벤트 저장소로 충분하다 |
| 모듈마다 별도 서비스(마이크로서비스) | 팀 데이터 격리·트랜잭션이 복잡해지고 포트폴리오 범위를 넘는다. 모듈러 모놀리스로 시작한다 |

## 결과

- 좋아지는 점: 모듈을 더하고 빼는 것이 코드 수준에서 보장된다. 이벤트를 잃지 않는다. 확장 모듈이 같은 규칙을 따른다.
- 감수하는 점: 이벤트 저장소 테이블과 전달기를 운영해야 한다. 구독자 처리는 원인보다 늦게 끝난다(최종 일관성). 시작 검증 때문에 계약을 어긴 모듈은 배포가 막힌다.
- 후속 작업: [docs/ai/backend.md](../ai/backend.md) 패키지 규칙을 새 구조로 바꾼다. OQ-55를 v0.1 시작 전에 정한다.
