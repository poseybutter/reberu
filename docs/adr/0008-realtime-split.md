# ADR-0008. 실시간: 저장은 API, 휘발은 실시간 채널

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [architecture/realtime.md](../architecture/realtime.md), [architecture/security.md](../architecture/security.md) 실시간 절

## 맥락

- 동료 입장·퇴장, 현재 상태, 위치, 인사, 업무 변경 같은 많은 변화가 새로고침 없이 보여야 한다.
- 실시간 연결로 저장까지 하면, 연결이 끊겼을 때 업무가 멈추고 권한·검증 경로가 API와 둘로 갈라진다.
- 위치처럼 초당 여러 번 바뀌는 값을 DB에 쓰면 부하가 크고 쓸모도 없다.
- 연회장처럼 많은 사람이 한 공간에 모이면 위치 메시지가 사람 수의 제곱으로 는다.

## 결정

- **DB에 남는 행동**(업무, 칭찬, 출석, 질문 등)은 일반 API로 처리하고, 처리가 끝난 뒤 결과만 실시간 이벤트로 알린다.
- **남기지 않는 것**(위치, 리액션, 차 마시기, 장작 넣기 등)은 실시간 채널로 바로 보내고 DB에 쓰지 않는다.
- 받는 범위를 개인, 팀, 공간, 조직 공간, 조직으로 나누고 가장 좁은 범위로 보낸다. 위치는 같은 공간 안에서만 오간다.
- 다시 연결되면 놓친 이벤트를 다시 보내지 않고, 지금 상태를 API로 한 번 다시 불러온다.
- 위치는 서버 메모리에만 둔다. 많은 사람이 모이는 공간은 가까운 사람의 위치만 자주 보내고, 앉은 사람은 위치를 보내지 않고, 리액션은 묶어 보낸다.
- 기술 후보는 Spring WebSocket + STOMP다. 의존성 추가는 따로 승인을 받는다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 모든 행동을 실시간 채널로 처리 | 연결이 끊기면 업무가 멈추고, 권한·검증이 두 갈래가 된다 |
| 놓친 이벤트를 순서대로 다시 보내기 | 서버가 사람마다 이벤트를 쌓아야 한다. 다시 불러오기로 충분하다 |
| SSE(서버 → 사용자 한 방향) | 위치를 사용자 쪽에서 자주 보내야 해서 맞지 않는다 |
| 위치를 DB에 저장 | 부하만 크고 쓸모가 없다 |

## 결과

- 좋아지는 점: 실시간 연결이 없어도 모든 업무가 된다. 권한 검증이 API 한 곳에 모인다. 범위를 좁혀 메시지 수를 줄인다.
- 감수하는 점: 서버가 다시 켜지면 위치가 처음 자리로 돌아간다. 다시 연결 때 불러오기 비용이 든다.
- 후속 작업: 이벤트 목록, 빈도 상한, 끊김 유예, 구독 권한을 [architecture/realtime.md](../architecture/realtime.md)에 요구사항으로 둔다.
