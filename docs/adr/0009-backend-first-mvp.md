# ADR-0009. 백엔드 우선 단계적 MVP

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [product/overview.md](../product/overview.md) §6

## 맥락

- 설계 범위가 넓다: 멀티 조직, 업무툴, 실시간, 3D 공간, 힐링 존, 조직 공간.
- 한 번에 모두 만들면 핵심(격리, 모듈 구조, 업무)을 증명하기 전에 범위가 무너진다.
- 이 프로젝트는 백엔드 설계 역량을 보여 주는 것이 우선이다.

## 결정

- **백엔드를 먼저** 만든다. 단계마다 API와 테스트로 완료를 확인하고, 화면은 그 단계의 API를 확인할 만큼만 붙인다.
- 단계를 아래층부터 쌓는다: v0.1 뼈대(로그인, 조직·팀, 가입, 모듈 구조) → v0.2 업무툴 → v0.3 함께(실시간 기반, 알림, 리포트, 첫 모듈) → v0.4 공간 → v0.5+ 모듈 더하기.
- 각 단계는 앞 단계를 고치지 않고 더하기만 한다. v0.5부터는 모듈 추가만으로 진행한다. 이 원칙이 깨지면 구조 결함으로 본다.
- v0.1에 테스트용 가짜 모듈을 등록해 모듈 구조를 실제 모듈 없이 증명한다.
- 단계마다 [architecture/security.md](../architecture/security.md)의 그 단계 보안 테스트를 통과해야 완료다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 3D 공간부터 만들기 | 눈에 띄지만 백엔드 핵심 증명이 늦어진다 |
| 기능을 화면 단위로 하나씩 완성 | 격리·모듈 같은 가로지르는 구조가 나중에 끼워 넣어져 앞 단계를 고치게 된다 |
| 프론트엔드와 동시 진행 | 범위가 두 배가 된다. 프론트엔드 기술은 v0.3 전에 정한다(OQ-24) |

## 결과

- 좋아지는 점: 단계마다 증명할 것이 분명하다. 모듈 구조가 맞는지 v0.5 이후 작업 방식으로 검증된다.
- 감수하는 점: v0.3 전까지 화면으로 보여 줄 것이 적다.
- 후속 작업: 단계별 이슈(로드맵)를 만든다. 단계 진입 전 미결 사항을 정한다.
