# ADR-0002. 고정 기능과 모듈 구조

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [product/overview.md](../product/overview.md) §5, [architecture/tenancy.md](../architecture/tenancy.md) 모듈 절, [architecture/security.md](../architecture/security.md) 모듈 절

## 맥락

- 단체마다, 직무마다 쓰는 기능이 다르다. 어떤 팀은 공간과 칭찬을 원하고, 어떤 팀은 업무와 리포트만 원한다.
- 복사해 쓰는 단체는 자기 직무에 맞는 기능(예: 특정 인증 관리)을 원한다. 이런 기능을 업스트림에 넣으면 업스트림이 특정 단체에 묶이고, 저장소 규칙(AGENTS.md 절대 규칙 3, CONTRIBUTING.md §3)에도 어긋난다.
- 복사한 저장소는 업스트림 파일을 고치지 않아야 태그 업데이트를 충돌 없이 받는다.
- 기존 앱의 기능 조사에서 "팀마다 기능 묶음을 켜고 끈다"는 요구가 확인됐다.

## 결정

- 기능을 **고정 기능**과 **모듈**로 나눈다. 고정 기능은 끌 수 없다: 업무, 프로젝트, 오늘의 할 일, 리포트, 출석, EXP·레벨·시즌, 알림, 조직·팀 관리.
- 모듈은 범위와 출처를 가진다.
  - 범위: `TEAM`(조직이 허용하고 팀이 켬) 또는 `ORG`(조직이 켬).
  - 출처: `BUNDLED`(reberu 저장소) 또는 `EXTENSION`(복사한 저장소의 자기 패키지).
- 팀 범위 모듈은 세 단계로 켠다: 설치됨(코드에 있음) → 조직이 허용 → 팀이 켬.
- 모듈은 하나의 등록 묶음으로 서버에 알린다: 모듈 정보(이름, 범위, 기본 켜짐, 의존), API와 필요 권한, 메뉴, 권한, EXP 출처, 알림 종류, 실시간 이벤트, 정해진 때 작업, 마이그레이션 위치.
- 모듈을 끄면 메뉴·화면·API·알림·EXP 출처가 사라지고, 기록은 남으며, 다시 켜면 이어진다. 테이블은 켜짐과 관계없이 마이그레이션으로 늘 만든다.
- 확장 모듈은 `db/migration/company`에 마이그레이션을 두고, 기본 제공 모듈은 `db/migration/core`에 둔다(CONTRIBUTING.md §3).
- core는 모듈 코드보다 먼저 지금 팀·권한·모듈 켜짐을 확인한다. 모듈이 이 확인을 끄거나 바꾸는 확장 지점은 두지 않는다.
- 팀을 만들 때 고르는 **직무 유형**이 켤 모듈과 항목의 기본값을 팀에 복사한다. 고정 기능의 규칙은 직무 유형이 바꾸지 못한다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 모든 기능을 고정으로 두고 설정 플래그로만 숨긴다 | 기능마다 플래그 검사가 흩어지고, 단체 전용 기능을 더할 방법이 없다 |
| 단체 전용 기능을 업스트림에 넣고 설정으로 켠다 | 업스트림이 특정 단체에 묶이고 저장소 규칙에 어긋난다 |
| 복사한 저장소가 업스트림 코드를 직접 고친다 | 태그를 받을 때마다 충돌이 난다 |
| 직무 유형이 고정 기능 규칙까지 바꾼다 | 팀마다 업무·EXP 규칙이 달라져 검증과 비교가 불가능해진다 |

## 결과

- 좋아지는 점: 기능을 더하고 빼도 core가 바뀌지 않는다. 단계(v0.5+)를 모듈 추가만으로 진행한다. 복사한 저장소가 충돌 없이 업데이트를 받는다.
- 감수하는 점: 모듈 계약(등록 묶음)을 처음부터 설계해야 한다. 모듈 사이 의존과 꺼짐 전파를 관리해야 한다.
- 후속 작업: 모듈 경계, 의존 방향, 모듈 사이 이벤트, 계약 인터페이스, 경계 테스트를 아키텍처 문서에서 정한다. v0.1에 테스트용 가짜 모듈로 구조를 검증한다([product/overview.md](../product/overview.md) PRD-MVP-12).
