# ADR-0016. 이벤트 저장소와 경계 검증: Spring Modulith

> 버전: v0.2.0\
> 수정일: 2026-11-06

- 상태: Accepted
- 영향: [architecture/modules.md](../architecture/modules.md) §4, §8, §10, [domain/model.md](../domain/model.md) §6, [docs/ai/backend.md](../ai/backend.md) §1, ARCH-EVT-09·10, ARCH-TEST-01·08, DOM-LIB-01·02

## 맥락

- [ADR-0014](0014-module-architecture.md)는 단위 사이 반응을 이벤트 저장소로 전달하고 경계를 테스트로 검사하기로 했다. 도구는 정하지 않았다.
- 이벤트 저장소는 원인과 같은 트랜잭션 기록, 커밋 뒤 구독자별 전달, 실패 재시도, 재시작 뒤 이어서 전달을 지켜야 한다(ARCH-EVT-01~04).
- 지원 DB가 셋이다([ADR-0013](0013-shared-db-portable-sql.md)).
- 외부 메시지 브로커는 쓰지 않지만 나중에 옮길 길은 남겨야 한다.

## 결정

- 이벤트 저장소와 전달은 Spring Modulith의 이벤트 발행 기록(JDBC)으로 한다.
- 경계 검증은 Spring Modulith 구조 검증으로 하고, 세 단위의 한 방향 규칙은 ArchUnit 규칙으로 함께 검사한다.
- 모듈 켜짐 확인(ARCH-EVT-05)은 core가 구독자 앞에서 한다. 꺼진 범위의 이벤트는 처리 없이 완료로 기록한다.
- 이벤트 발행 기록 표의 DDL은 Flyway가 DB별 위치에서 만든다. 라이브러리의 자동 스키마 생성은 끈다.
- 외부 메시지 브로커가 필요해지면 Spring Modulith의 이벤트 외부 발행 기능으로 옮긴다([architecture/modules.md](../architecture/modules.md) §4.2).

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 이벤트 저장소와 전달기를 직접 만든다 | 트랜잭션 연결, 재시도, 재시작 복구를 직접 만들고 시험해야 한다. 같은 요구사항을 이미 지키는 라이브러리가 있다 |
| Kafka 같은 외부 메시지 브로커 | 서버 한 대 규모에서 운영 부담이 크고, 복사해 쓰는 단체도 브로커를 운영해야 한다. 이벤트 양이 브로커가 필요한 수준이 아니다 |
| ArchUnit만으로 경계 검증 | 가능하지만 단위 정의와 허용 의존을 규칙으로 모두 직접 써야 한다. Spring Modulith 검증 위에 부족한 규칙만 ArchUnit으로 더한다 |

## 결과

- 좋아지는 점: 이벤트를 잃지 않는 전달을 검증된 구현으로 얻는다. 세 DB의 표 정의가 라이브러리에 있다. 브로커로 옮길 때 업무 코드와 이벤트 레코드를 고치지 않는다.
- 감수하는 점: 라이브러리 판을 Spring Boot 판과 함께 올려야 한다. 이벤트 발행 기록 표는 라이브러리가 열 구조를 정하므로 우리 타입 규칙의 예외다(DOM-LIB-01). MySQL·MariaDB의 시각 열은 `TIMESTAMP(6)`이라 2038년 1월 19일까지만 담는다. 라이브러리가 열 구조를 바꾸면 그 판을 따라 새 마이그레이션을 더한다.
- 후속 작업: 의존성 추가(Spring Modulith)는 구현 시작 때 따로 승인을 받는다. 재시도 간격과 보관 기간은 구현 단계에서 정한다.
