# ADR-0006. 조직·팀 데이터 격리와 비노출 응답

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [architecture/tenancy.md](../architecture/tenancy.md) 격리 절, [architecture/security.md](../architecture/security.md) 권한 절, [domain/rules.md](../domain/rules.md)

## 맥락

- 한 사람이 여러 조직·팀에 속한다. 팀마다 업무·출석·EXP를 어떻게 셀지 정해야 했다(팀별인가, 사람별인가).
- 다른 팀 업무 번호를 넣어 조회하는 공격(IDOR)은 멀티 테넌트 서비스의 가장 흔한 결함이다.
- 권한이 없다는 응답과 없다는 응답이 다르면, 응답만으로 다른 조직·팀에 무엇이 있는지 알아낼 수 있다.

## 결정

- 업무, 프로젝트, 할 일, 리포트, 회의, 출석, EXP·레벨·시즌, 업적, 알림, 휴식 기록, 꾸미기는 모두 **팀에 속한다.** 팀은 반드시 조직 하나에 속하고 조직을 옮기지 않는다.
- 여러 팀에 속한 사람도 팀마다 따로 기록한다. 팀을 옮기면 새 팀에서 레벨 1부터 시작한다.
- 조직 공간 모듈의 데이터(연회장 모임, 공용 회의)와 조직 설정은 **조직에 속한다.** 조직 데이터는 팀 데이터를 참조하지 않는다.
- 팀 데이터 API는 주소에 팀을, 조직 데이터 API는 주소에 조직을 넣는다(`/api/teams/{teamId}/...`, `/api/orgs/{orgId}/...`).
- 서버는 요청마다 조직 멤버십 → 팀 소속 조직 → 팀 멤버십 → 역할 → 모듈 켜짐 순서로 확인하고 지금 팀(`TeamContext`)을 정한다. 사용자가 보낸 팀 번호를 믿지 않는다.
- 팀 데이터는 늘 "이 팀의 이 번호"로 찾는다. 번호만으로 찾지 않는다.
- 다른 조직·팀의 자원, 꺼진 모듈, 권한 없는 자원은 모두 **"찾을 수 없음"**으로 같게 응답한다.
- 업무의 프로젝트·담당자, 팀 회의 참석자는 같은 팀의 것이어야 한다. 저장할 때 확인한다.
- 조직 관리자는 자기 조직 모든 팀의 관리 권한을 갖지만 그 팀의 팀원은 아니다. 출석·EXP가 쌓이지 않고 공간에 들어가지 않는다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 출석·EXP를 사람 기준 하나로 | 팀마다 다른 활동이 섞여 팀 기록이 무의미해진다. 한 팀의 기록이 다른 팀에 보인다 |
| 프로젝트를 여러 팀이 공유 | 팀 격리에 예외가 생기고 권한 판단이 복잡해진다 |
| 권한 없음은 403, 없음은 404 | 응답 차이로 다른 조직·팀의 자원 존재를 알아낼 수 있다 |

## 결과

- 좋아지는 점: 격리 규칙이 단순하고 테스트가 쉽다. 팀 단위로 데이터를 지우거나 내보낼 수 있다.
- 감수하는 점: 팀 사이 협업은 조직 공간 모듈로만 한다. 사용자 입장에서 권한 문제와 없는 자원을 구별할 수 없다.
- 후속 작업: 모든 팀·조직 데이터 API에 다른 조직·팀 접근 테스트를 둔다. 조직 하나 모드에서도 이 테스트를 돌린다.
