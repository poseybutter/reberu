# ADR-0005. 가입 정책: 공개 범위와 가입 방법

> 버전: v0.1.0\
> 수정일: 2026-11-04

- 상태: Accepted
- 영향: [architecture/tenancy.md](../architecture/tenancy.md) 가입 절, [architecture/security.md](../architecture/security.md) 초대·공개 조직 절, [product/screens.md](../product/screens.md) A0~A6, E2, F5, F7

## 맥락

- 처음 설계는 이메일 도메인으로 내부 구성원과 외부 사용자를 나눴다. 허용 도메인의 사람은 내부, 그 밖은 외부 초대로만 들어왔다.
- 이 방식은 자기 도메인을 가진 단체에만 맞는다. 동아리, 스터디, 작은 단체는 대개 개인 Gmail을 쓰므로 도메인으로 사람을 가를 수 없다.
- 누구나 쓰는 서비스에서는 단체마다 들어오는 방식이 다르다. 비공개로 초대만 받는 곳, 공개로 찾아오게 하는 곳, 도메인 사람을 자동으로 받는 곳이 있다.
- 관리자가 이메일을 미리 넣어 두면 그 사람이 로그인할 때 바로 그 조직·팀으로 들어와야 한다.
- 협력사, 외부 강사처럼 잠시 함께하는 사람은 권한과 기간을 제한해야 한다.

## 결정

- 조직과 팀은 각각 **공개 범위**를 가진다. `PRIVATE`(비공개, 기본)는 찾기에 보이지 않고 초대로만 들어온다. `PUBLIC`(공개)은 찾기에 보이고 가입 요청을 받는다.
- 조직은 **가입 방법**을 블록처럼 켜고 끈다.
  - 이메일 초대: 늘 켜짐. 그 이메일로 로그인하면 바로 그 조직·팀에 들어온다.
  - 초대 링크: 기본 켜짐. 팀, 승인 필요 여부, 기본 역할, 만료일(필수), 사용 횟수를 정한다.
  - 가입 요청: 공개 조직에서만. 승인 필요 또는 바로 가입.
  - 도메인 자동 가입: 기본 꺼짐. DNS로 소유를 확인한 도메인만. v0.3.
- 멤버 종류(`MEMBER`/`GUEST`)는 **도메인이 아니라 초대할 때** 정한다. 손님은 이메일 초대로만 들어오고, 기간이 필수이며, 관리자가 될 수 없고, 초대받은 팀만 본다.
- 손님 초대는 기본으로 조직 관리자 승인이 필요하다. 조직 설정으로 끌 수 있다.
- 어떤 가입 방법으로도 관리자 역할을 줄 수 없다.
- 조직에 들어와도 팀 데이터는 팀 멤버십이 있어야 보인다. 공개 조직의 "바로 가입"은 조직 공간과 공개 팀 목록까지만 연다.

## 검토한 대안

| 대안 | 버린 이유 |
| --- | --- |
| 도메인으로 내부/외부를 판별 | 도메인이 없는 단체가 쓸 수 없다. 개인 Gmail 사용자를 모두 외부로 다룬다 |
| 초대만 허용 | 공개 스터디·커뮤니티가 사람을 모을 수 없다 |
| 공개 조직에 누구나 바로 들어와 팀 데이터까지 열람 | 공개 범위와 업무 데이터 열람이 묶여 정보가 새어 나간다 |
| 도메인 자동 가입을 기본으로 | 남의 도메인을 가로채는 위협이 생긴다. 소유 확인 없이 켤 수 없다 |

## 결과

- 좋아지는 점: 비공개 단체, 공개 커뮤니티, 도메인 단체를 같은 모델로 다룬다. 가입 방법을 더해도 모델이 바뀌지 않는다.
- 감수하는 점: 비공개 조직의 존재를 응답 차이로도 드러내지 않게 모든 실패 응답을 같게 해야 한다. 공개 조직 검색과 가입 요청에 남용 대책이 필요하다.
- 후속 작업: 가입 방법별 흐름과 상태 전이를 [architecture/tenancy.md](../architecture/tenancy.md)에, 토큰·검색·요청 제한을 [architecture/security.md](../architecture/security.md)에 둔다.
