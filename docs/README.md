# reberu 문서

> 버전: v0.2.0\
> 수정일: 2026-11-04

reberu의 제품·도메인·아키텍처 기준 문서다. 도메인 모델, API 명세, 구현, 테스트는 이 문서들을 근거로 삼는다. 진행 상황은 문서에 쓰지 않고 이슈와 커밋으로 관리한다.

## 1. 문서 지도

### 1.1 폴더 구조

```
docs/
├── README.md              문서 지도, 작성 규칙, 용어집, 미결 사항 (이 문서)
├── product/               무엇을, 왜 만드는가 — 사용자에게 보이는 제품
│   ├── overview.md          목적, 목표·비목표, 역할, 원칙, 기능 구성, MVP 단계
│   ├── flows.md             사용자 흐름
│   ├── spaces.md            화면 방향, 공간 명세
│   └── screens.md           화면 명세
├── domain/                무엇이 참인가 — 기술과 관계없는 업무 규칙
│   ├── rules.md             업무, 출석, EXP·레벨·시즌, 업적, 휴식, 리포트 규칙
│   └── model.md             엔티티, 관계, 제약, 소속, 멱등 키
├── architecture/          어떻게 만드는가 — 백엔드 설계

│   └── modules.md           core·고정 기능·모듈 경계, 의존 방향, 도메인 이벤트, 모듈 계약
```

### 1.2 폴더를 나누는 기준

| 폴더 | 답하는 질문 | 바뀌는 이유 | 주 독자 |
| --- | --- | --- | --- |
| `product/` | 무엇을, 왜 만드는가. 사용자에게 어떻게 보이는가 | 제품 방향, 화면, 사용 흐름이 바뀔 때 | 기획·디자인·프론트엔드 |
| `domain/` | 기술과 관계없이 무엇이 참인가 | 업무 규칙이 바뀔 때 | 백엔드·기획 |
| `architecture/` | 어떻게 만드는가 | 기술 선택, 구조, 보안 요구가 바뀔 때 | 백엔드 |
| `adr/` | 왜 그렇게 정했는가 | 새 결정이 생기거나 이전 결정을 뒤집을 때 | 전원 |
| `ai/` | AI 에이전트가 어떻게 작업하는가 | 작업 규칙이 바뀔 때 | AI 에이전트 |

- 새 문서는 위 질문으로 자리를 정한다. 한 문서가 두 질문에 답하면 더 무거운 쪽에 두고 다른 쪽에서 링크한다.
- 다음에 생길 문서의 자리: API 목록은 `architecture/api.md`. 배포·운영 문서가 생기면 `operations/`를 더한다.
- 폴더 안 문서 이름은 번호 없이 내용으로 짓는다. 읽는 순서는 아래 §1.3이 정한다.

## 2. 작성 규칙

### 2.1 문체

- 평서체(`~한다`)와 개조식으로 쓴다. 한 문장에 한 사실만 쓴다.
- 결정은 단정한다. 추측, 권유, 대화체를 쓰지 않는다. 정하지 않은 것은 미결 사항(§5)으로 보내고 본문에는 "OQ-xx"로만 가리킨다.
- 같은 개념은 늘 같은 용어(§4)로 쓴다. 동의어를 섞지 않는다.
- 쓰임새는 "회사, 동아리, 스터디 등 어떤 단체든"으로만 적고, 특정 단체를 전제로 쓰지 않는다.
- 예시 데이터는 지어낸 값만 쓴다. 사람은 "다온", "하늘", 조직은 "파도 조직", "구름 조직", 팀은 "바다팀", "숲팀", 도메인은 `example.com`.

### 2.2 요구사항 표기

| 수준 | 뜻 |
| --- | --- |
| **필수** | 지키지 않으면 결함이다. 테스트로 확인한다 |
| **권장** | 따르지 않으려면 이유를 ADR이나 PR에 남긴다 |
| **선택** | 구현 여부를 단계에서 정한다 |

요구사항 ID는 `영역-분류-번호` 형식이다(예: `SEC-AUTH-01`). 한 번 붙인 ID는 바꾸거나 다시 쓰지 않는다. 지운 요구사항의 ID는 비워 둔다.

| 접두어 | 영역 | 문서 |
| --- | --- | --- |
| `PRD` | 제품 범위 | `product/overview.md` |
| `TEN` | 테넌시·멤버십·권한 | `architecture/tenancy.md` |
| `SEC` | 보안 | `architecture/security.md` |
| `RT` | 실시간 | `architecture/realtime.md` |
| `ARCH` | 모듈 구조 | `architecture/modules.md` |
| `RULE` | 도메인 규칙 | `domain/rules.md` |
| `DOM` | 도메인 모델 | `domain/model.md` |
| `UX` | 흐름·공간·화면 | `product/flows.md`, `product/spaces.md`, `product/screens.md` |

### 2.3 그림과 흐름

- 상태 전이는 Mermaid `stateDiagram-v2`, 순서는 `sequenceDiagram`, 분기는 `flowchart`로 그린다.
- 흐름도의 모든 분기에는 조건을 적고, 모든 끝에는 결과(상태, 응답, 화면)를 적는다.
- 상태 이름은 코드에서 쓸 대문자 상수(`ACTIVE` 등)로 쓰고, 처음 나올 때 한국어 이름을 함께 적는다.

### 2.4 머리말과 버전

`docs/` 아래 모든 Markdown 문서는 제목 바로 아래에 머리말을 둔다.

```markdown
# 문서 제목

> 버전: v0.1.0\
> 수정일: 2026-11-04
```

| 바꾼 내용 | 올리는 자리 | 예 |
| --- | --- | --- |
| 오탈자, 문장 다듬기, 링크 고침처럼 뜻이 바뀌지 않는 변경 | PATCH | v0.1.0 → v0.1.1 |
| 요구사항·규칙·흐름의 추가나 변경, 미결 사항 결정 반영 | MINOR | v0.1.1 → v0.2.0 |
| 문서 구조 재편, 이미 쓰인 요구사항 ID·용어의 의미 변경 | MAJOR | v0.2.0 → v1.0.0 |

- 버전 줄 끝의 `\`는 두 줄이 따로 보이게 하는 Markdown 줄바꿈이다. 검사는 이 문자가 있어도 없어도 받아들인다.
- 수정일은 `YYYY-MM-DD` 형식이며 그 문서를 마지막으로 고친 날로 쓴다. 같은 날 여러 번 고치면 날짜는 그대로 두고 버전만 올린다.
- PR에서 문서를 고치면 버전을 반드시 올리고 수정일을 고친 날로 맞춘다. 새 문서는 `v0.1.0`으로 시작한다.
- 이 규칙은 PR 검사(`.github/workflows/docs.yml`)가 확인한다. 버전이 오르지 않았거나, 수정일이 그 파일을 마지막으로 고친 커밋 날짜와 하루 넘게 다르거나, 머리말 형식이 틀리면 PR 검사가 실패한다.

### 2.5 식별자

- 화면: [product/screens.md](product/screens.md)의 번호(`A0`~`F8`, `B12` 등)를 쓴다.
- 실시간 이벤트: `도메인.동사-과거형`(예: `task.changed`)을 쓴다.
- API 경로 예시: 팀 데이터 `/api/teams/{teamId}/...`, 조직 데이터 `/api/orgs/{orgId}/...`, 내 계정 `/api/me/...`.
- 문서 사이 참조는 "문서 링크 + § 절 번호"로 쓴다(예: [architecture/tenancy.md](architecture/tenancy.md) §6).

## 3. 범위 밖

- 테이블·컬럼·인덱스 설계 (도메인 모델 문서에서 다룬다)

## 4. 용어집

### 4.1 구조

| 용어 | 코드 이름 | 정의 |
| --- | --- | --- |
| 배포 | `Deployment` | 실행 중인 reberu 서버 하나. 설치된 모듈, 배포 모드, 비밀값은 배포 단위로 정하며 데이터로 저장하지 않는다 |
| 배포 모드 | `DeploymentMode` | `MULTI_ORG`(조직 만들기 모드, 기본) 또는 `SINGLE_ORG`(조직 하나 모드) |
| 조직 | `Organization` | 함께 일하거나 활동하는 단체. 팀, 조직 설정, 조직 소속 데이터를 가진다 |
| 팀 | `Team` | 조직 안에서 함께 일하는 단위. 반드시 조직 하나에 속한다. 업무·출석·EXP 등 대부분의 데이터는 팀에 속한다 |
| 계정 | `Account` | Google 계정 하나에 대응하는 사람. 배포 전체에 하나이며 Google `sub`로 식별한다 |
| 조직 멤버십 | `OrgMembership` | 계정 × 조직. 멤버 종류, 조직 관리자 여부, 상태를 가진다 |
| 팀 멤버십 | `TeamMembership` | 계정 × 팀. 팀 역할, 상태를 가진다. 같은 조직의 활동 조직 멤버십이 있어야 활동 상태가 될 수 있다 |
| 지금 팀 | `TeamContext` | 요청 하나를 처리하는 동안 서버가 확정한 조직·팀·멤버십·역할·켜진 모듈 묶음 |

### 4.2 사람과 권한

| 용어 | 코드 이름 | 정의 |
| --- | --- | --- |
| 멤버 종류 | `MemberKind` | 조직 안에서의 신분. `MEMBER`(구성원) 또는 `GUEST`(손님). 들어올 때의 초대·가입 방법이 정한다 |
| 구성원 | `MEMBER` | 조직에서 함께 일하는 사람 |
| 손님 | `GUEST` | 기간을 정해 초대받은 팀에만 들어오는 사람. 관리자가 될 수 없다 |
| 조직 관리자 | `orgAdmin` | 조직 멤버십에 붙는 권한. 조직 설정과 그 조직 모든 팀의 관리 권한을 가진다 |
| 팀 역할 | `TeamRole` | `TEAM_ADMIN`(팀 관리자), `TEAM_MEMBER`(팀원), `VIEWER`(읽기 전용) |
| 계정 종류 | `GoogleAccountKind` | `WORKSPACE`(ID 토큰에 `hd`가 있는 Google Workspace 계정) 또는 `PERSONAL`(개인 Google 계정). 기능 안내에만 쓰고 권한 판정에 쓰지 않는다 |
| 운영자 | `Operator` | 배포를 운영하는 사람. 조직 정지만 할 수 있다(OQ-26) |

### 4.3 가입

| 용어 | 정의 |
| --- | --- |
| 공개 범위 | 조직·팀이 찾기에 보이는지. `PRIVATE`(비공개, 기본) 또는 `PUBLIC`(공개) |
| 가입 방법 | 조직이 켜고 끄는 들어오는 길. 이메일 초대, 초대 링크, 가입 요청, 도메인 자동 가입 |
| 이메일 초대 | 이메일·팀·역할·멤버 종류를 미리 넣어 두고, 그 이메일로 로그인하면 들어오게 하는 초대 |
| 초대 링크 | 토큰이 담긴 주소. 열면 정해진 팀에 들어오거나 가입을 요청한다 |
| 가입 요청 | 공개 조직이나 공개 팀에 들어가려는 요청 |
| 도메인 자동 가입 | 소유를 확인한 도메인의 이메일로 로그인하면 구성원으로 들어오게 하는 방법 |

### 4.4 기능

| 용어 | 정의 |
| --- | --- |
| 고정 기능 | 모든 팀에 늘 있고 끌 수 없는 기능: 업무, 프로젝트, 오늘의 할 일, 리포트, 출석, EXP·레벨·시즌, 알림, 조직·팀 관리 |
| 모듈 | 켜고 끌 수 있는 기능 단위. 범위와 출처로 나눈다 |
| 모듈 범위 | `TEAM`(팀 범위: 조직이 허용하고 팀 관리자가 켬) 또는 `ORG`(조직 범위: 조직 관리자가 켬) |
| 모듈 출처 | `BUNDLED`(기본 제공: reberu 저장소에 있음) 또는 `EXTENSION`(확장: 복사한 저장소가 자기 패키지에 더함) |
| 외부 알림 | 알림을 reberu 밖 메신저로 보내는 팀 범위 모듈. 첫 제공자는 Google Chat 웹훅이다 |
| 웹훅 주소 | Google Chat 방에 글을 쓸 수 있는 키가 든 주소. 비밀값으로 다룬다 |
| 직무 유형 | 팀을 만들 때 고르는 기본값 묶음. 켤 모듈, 업무 구분 라벨, 추가 항목, 리포트 설정을 팀에 복사한다 |

### 4.5 공간과 일상

| 용어 | 정의 |
| --- | --- |
| 공간 | 걸어 다니는 3D 장소. 일하다 쉬러 가는 휴식·교류 공간이며 업무 기능을 두지 않는다. 팀 공간(로비, 내 자리, 라운지, 회의실, 바닷가, 산길)과 조직 공간(광장, 연회장)이 있다 |
| 업무 패널 | 공간 화면에서 늘 같은 자리에 있는 업무 요약 영역 |
| 현재 상태 | `AVAILABLE`(한가함), `FOCUS`(집중 중), `MEETING`(회의 중), `AWAY`(자리 비움). `AWAY`의 무활동 전환 외에는 모두 사용자가 직접 고른다 |
| 근무일 | 월~금 가운데 조직 휴일 달력에 없는 날 |
| 출석 | 근무일에 팀을 처음 연 순간 서버가 남기는 기록 |
| 휴식 | 힐링 존에서 불멍·물멍·요가·걷멍·산멍을 한 기록. EXP를 주지 않는다 |

## 5. 미결 사항

정하면 이 표에서 지우고 해당 문서와 ADR에 반영한다. 번호는 다시 쓰지 않는다. 단계마다 먼저 정할 항목은 [product/overview.md](product/overview.md)의 MVP 단계 절에 둔다.

| ID | 질문 | 현재 가정 |
| --- | --- | --- |
| OQ-01 | 오늘의 퀘스트를 누가 정하나 | 서버가 공통 목록에서 매일 3개를 뽑는다 |
| OQ-02 | 퀘스트를 어떻게 체크하나 | 행동으로 확인되는 퀘스트만 두고 자동 체크한다 |
| OQ-04 | 힐링 존에 있을 때의 현재 상태 | `AVAILABLE`로 두고 위치로 휴식 중임을 보인다 |
| OQ-05 | 명예의 전당이 평가 압박이 되는 문제 | 팀 범위 모듈로 두어 끌 수 있게 한다 |
