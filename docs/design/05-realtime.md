# 실시간 변화

[04-screens.md](04-screens.md)의 "실시간" 항목을 한곳에 모아, 백엔드 실시간 기능을 설계하는 근거로 씁니다. 기술 선택(아래 "기술 후보")은 아직 확정이 아닙니다.

## 기본 원칙

1. **저장하는 행동은 API로, 알리는 것은 실시간으로.** 업무 완료, 칭찬, 출석처럼 DB에 남는 행동은 일반 API로 처리하고, 처리가 끝난 결과만 실시간으로 알립니다. 실시간 연결이 끊겨도 업무는 됩니다.
2. **남기지 않는 것만 실시간으로 바로 보낸다.** 위치, 리액션, 차 마시기처럼 기록할 필요가 없는 것은 실시간 연결로 바로 주고받고 DB에 쓰지 않습니다.
3. **받을 사람만 받는다.** 받는 범위를 개인, 팀, 공간 셋으로 나누고, 가장 좁은 범위로 보냅니다. 특히 위치는 같은 공간 안에서만 오갑니다.
4. **놓친 것은 다시 불러온다.** 끊겼다가 다시 연결되면 놓친 이벤트를 하나씩 다시 보내지 않고, 지금 상태를 API로 한 번 다시 불러옵니다.

## 받는 범위

| 범위 | 받는 사람 | 듣기 시작 | 그만 듣기 |
| --- | --- | --- | --- |
| 개인 | 나 한 명 | 로그인하고 연결할 때 | 연결이 끊길 때 |
| 팀 | 지금 그 팀을 보고 있는 구성원 | 팀에 들어갈 때 (A3, B1) | 팀을 바꾸거나 나갈 때 |
| 공간 | 지금 그 공간에 있는 사람 | 공간에 들어갈 때 | 다른 공간으로 옮길 때 |
| 조직 공간 | 지금 광장·연회장·공용 회의실 하나에 있는 사람 (팀과 관계없음) | 조직 공간에 들어갈 때 | 나올 때 |
| 조직 | 조직의 활동 계정 모두 | 로그인하고 연결할 때 | 연결이 끊길 때 |

- 조직 범위는 연회장 모임 시작·일정처럼 조직 전체에 알릴 것에만 씁니다. 자주 바뀌는 것은 보내지 않습니다.

- 팀 범위는 그 팀의 활동 멤버만, 공간 범위는 지금 그 공간에 있는 사람만 들을 수 있게 서버가 확인합니다. 확인 규칙은 API와 같습니다([06-multi-team.md](06-multi-team.md#서버가-지키는-규칙)).
- 멤버십이 끝나면(내보내기, 정지, 팀 보관, 계정 정지) 서버가 그 사람의 팀·공간 범위 듣기를 바로 끊습니다.
- 조직 관리자는 팀 범위를 듣지 않습니다. 관리 화면은 들어올 때 불러옵니다.
- 관리자에게만 가는 것(새 가입 요청 등)은 팀 범위 안에서 관리자에게만 보냅니다.

## 이벤트 목록

**보내는 길**은 이벤트가 어떻게 생기는지입니다.
- API 뒤: API 처리가 끝난 뒤 서버가 보냄
- 직접: 사용자가 실시간 연결로 보낸 것을 서버가 그대로 퍼뜨림
- 서버: 서버가 스스로 판단해서 보냄

**저장**은 DB에 남는지를 뜻합니다.

## 위치 주고받기

- **보내는 때**: 움직이는 동안만 보냅니다. 멈추면 마지막 위치를 한 번 보내고 그칩니다.
- **빈도**: 초안은 **1초에 최대 5번**(200ms마다)입니다. 받는 쪽은 사이를 부드럽게 이어 그립니다. 운영하면서 조정합니다.
- **담는 것**: 공간 안 좌표(x, z), 바라보는 방향, 걷는 중 여부. 앉으면 좌표 대신 자리 번호를 보냅니다.
- **서버가 하는 일**: 공간 경계 밖 좌표는 버리고, 너무 자주 오면 빈도에 맞게 덜어 냅니다. 같은 공간의 다른 사람에게만 퍼뜨립니다.
- **저장하지 않음**: 위치는 서버 메모리에만 두고 DB에 쓰지 않습니다. 서버가 다시 켜지면 모두 들어온 공간의 처음 자리에서 시작합니다.
- **규모 어림**: 한 공간에 8명이 모두 걷는 경우, 서버로 들어오는 것은 초당 40번, 나가는 것은 초당 280번(8명 × 동료 7명 × 5번)입니다. 서버 한 대로 감당할 수 있는 크기로 봅니다.

## 많은 사람이 모일 때 (조직 공간)

팀 공간은 정원이 작아 모두에게 모든 위치를 보내도 되지만, 연회장에 조직 전체가 모이면 위치 메시지가 사람 수의 제곱으로 늘어납니다. 예를 들어 100명이 모두 1초에 5번 움직이면 서버가 내보내는 메시지는 초당 약 5만 개입니다. 그래서 조직 공간은 아래 규칙을 씁니다.

| 규칙 | 내용 |
| --- | --- |
| 가까운 사람만 자주 | 공간을 칸으로 나누고, 내 칸과 이웃 칸에 있는 사람의 위치만 1초에 최대 5번 받습니다 |
| 먼 사람은 드물게 | 그 밖의 사람은 2초에 한 번 몰아서 받습니다 |
| 길 위에서는 진행 정도만 | 산길을 자동으로 걸을 때는 좌표 대신 "어느 구간을 얼마나 왔는지"와 빠르기만 보냅니다. 받는 쪽이 길을 따라 이어 그리므로 5초에 한 번이면 충분합니다. 팀 공간에도 같은 방식을 씁니다 |
| 앉은 사람은 보내지 않음 | 연회장에서 테이블에 앉으면 자리 번호만 한 번 보내고, 일어날 때까지 위치를 보내지 않습니다. 연회장 모임 중에는 대부분 앉아 있으므로 부담이 크게 줄어듭니다 |
| 리액션은 묶어서 | 리액션 하나하나를 퍼뜨리지 않고 서버가 1초마다 종류별 수로 묶어 보냅니다 |
| 질문은 API로 | 질문과 "나도 궁금해요"는 저장하는 행동이므로 API로 처리하고 결과만 알립니다 |

- 이 규칙으로 100명이 모인 연회장에서도 서버 한 대로 감당하는 것을 목표로 합니다. 실제 수치는 부하 테스트로 확인합니다.
- 연회장 정원을 넘는 사람은 단순하게 보기로 참여합니다. 위치는 주고받지 않고 안건·질문·리액션만 받습니다.

## 접속과 끊김

| 상황 | 처리 |
| --- | --- |
| 연결 | 로그인한 세션으로만 연결합니다. 연결되면 개인 범위를 듣습니다. |
| 접속 확인 | 서버와 주기적으로 신호를 주고받습니다. 간격은 기술을 정할 때 정합니다. |
| 끊김 | **30초** 동안 기다립니다. 그 안에 다시 연결되면 아무 일도 없던 것으로 봅니다. 넘으면 공간에서 조용히 사라지고 `presence.offline`을 보냅니다 ([01-daily-flow.md](01-daily-flow.md) 예외 흐름). |
| 다시 연결 | 공간·안 읽은 알림 수·업무 패널을 API로 다시 불러오고, `space.snapshot`을 받습니다. 놓친 이벤트는 다시 보내지 않습니다. |
| 여러 탭·기기 | 공간에는 한 명으로 보입니다. 위치는 가장 최근에 움직인 탭을 따르고, 모든 탭이 끊겨야 나간 것으로 봅니다. |
| 업무 화면(C·D) | 공간에 있는 것으로 그대로 둡니다. 내 아바타는 마지막 자리에 머뭅니다 ([04-screens.md](04-screens.md) C0). |

## 모듈과 실시간

- 공간 범위의 이벤트는 공간 모듈을 켠 팀에만 있습니다. 공간을 끈 팀은 개인·팀 범위만 씁니다.
- 조직 공간·조직 범위의 이벤트는 조직이 조직 공간 모듈을 켰을 때만 있습니다. 팀의 공간 모듈과는 관계없어서, 팀 공간을 끈 팀의 사람도 조직 공간에는 들어갈 수 있습니다.
- 끈 모듈의 이벤트는 보내지 않습니다. 모듈을 끄면 `team.modules-changed`를 받은 화면이 그 모듈의 메뉴와 화면을 닫습니다.
- 조직 모듈도 같은 세 범위로 이벤트를 더할 수 있게 확장 지점을 둡니다.

## 서버가 정해진 때 만드는 알림

| 알림 | 언제 | 기능 |
| --- | --- | --- |
| 업무 마감 임박 | 마감 전날과 당일 아침 | 고정 |
| 업무 마감 지남 | 마감 다음 날 아침 | 고정 |
| 인증 만료 임박 | 만료 전 정해진 날(예: 45일, 7일 전) | 모듈: 인증·만료일 관리 |

- 정해진 때 서버가 알림을 만들고, 접속해 있으면 `notification.created`로 바로 보냅니다. 접속해 있지 않으면 다음에 들어올 때 알림 목록에서 봅니다.
- 아침 요약(모듈)은 알림을 따로 보내지 않고, 첫 출근 때 B1에 카드로 보여 줍니다.

## 알림과 방해 금지

- 서버가 알림을 만들 때 받는 사람의 알림 설정(D2)을 확인합니다.
  - 그 종류를 꺼 두었으면: 만들지 않습니다.
  - 방해 금지 시간이면: 알림 목록(D1)에는 저장하되, 잠깐 뜨는 알림은 띄우지 않습니다.
- 힐링 존에서 멍하는 동안에는 알림을 저장만 하고 화면에 띄우지 않습니다. 멍하기를 끝내면 모아 둔 알림 수를 한 번 보여 줍니다(제안 #5를 힐링 존에 적용).

## 기술 후보 (확정 전)

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| **Spring WebSocket + STOMP** (추천) | 범위를 주소(개인·팀·공간)로 나누기 쉬움. Spring Security로 듣기 권한 확인. 서버를 늘릴 때 메시지 중계기(Redis 등)로 바꾸기 쉬움 | STOMP 규칙을 따로 익혀야 함 |
| WebSocket만 쓰기 | 가볍고 자유로움 | 범위 나누기, 권한 확인, 재연결을 직접 만들어야 함 |
| SSE (서버 → 사용자 한 방향) | 단순함 | 위치를 사용자 쪽에서 자주 보내야 해서 맞지 않음 |

- 처음에는 서버 한 대, 메모리 안 중계로 시작합니다. 서버를 늘려야 할 때 중계기를 붙입니다.
- 정하면 [docs/ai/backend.md](../ai/backend.md)의 기술 결정에 옮기고, 의존성 추가는 그때 따로 승인을 받습니다.
