# 멀티팀 구조

조직, 팀, 사람, 직무 유형, 기능 모듈이 어떻게 엮이는지 정합니다. 도메인 모델과 권한 설계의 기준입니다. 이름 옆 `영어 이름`은 코드에서 쓸 개념 이름 후보이며, 테이블·컬럼 이름은 도메인 모델 단계에서 정합니다.

## 정한 것 (2026-11-04)

| 질문 | 결정 |
| --- | --- |
| 조직과 팀의 계층 | **배포 1개 = 조직 1개.** 조직 아래에 팀 여러 개 |
| 직무별 구분 | **팀마다 직무 유형을 고름.** 직무 유형이 모듈과 항목의 기본값을 채우고, 팀은 그 뒤에 바꿀 수 있음 |
| 팀 사이 데이터 | **팀마다 완전히 분리.** 업무, 프로젝트, 리포트, 출석, EXP 모두 팀 소속. 여러 팀에 속한 사람도 팀마다 따로 기록 |
| 관리자 단계 | **조직 관리자 + 팀 관리자** |
| 팀을 넘어 모이기 | **조직 공간 모듈**(광장, 연회장, 공용 회의실). 그 기록은 조직에 속하고 팀 데이터와 섞이지 않음 (아래 "조직 소속 데이터") |
| 출석의 날짜 기준 | **조직 하나에 시간대 하나, 휴일 달력 하나.** 모든 팀이 같은 근무일을 씀 ([출석 규칙](03-progression.md#출석-규칙-고정)) |

이 결정으로 [README의 정하지 못한 점](README.md#정하지-못한-점과-부딪히는-점) #7(여러 팀의 출석), #8(EXP와 레벨 단위), #9(가입 요청의 대상)가 정해졌습니다.

메타버스(3D 공간, 걷기)는 공간 모듈 안에서만 쓰입니다. 이 문서의 구조는 공간을 켜든 끄든 같습니다.

## 개념 계층

```
조직 (배포 하나에 하나)
 ├─ 사람(계정) ─────────────┐
 ├─ 직무 유형 (팀 기본값 묶음)  │ 멤버십 (사람 × 팀, 팀 역할)
 ├─ 조직에서 허용한 모듈        │
 └─ 팀 ◀───────────────────┘
     ├─ 직무 유형 (만들 때 고름)
     ├─ 팀 설정, 켠 모듈
     └─ 팀 소속 데이터: 업무, 프로젝트, 할 일, 리포트, 회의, 출석, EXP, 업적, 알림, 공간
```

| 개념 | 설명 |
| --- | --- |
| 조직 `Organization` | 배포 하나에 하나뿐입니다. 조직 이름, 시간대, 휴일 달력, 로그인 허용 기준, 조직에서 허용한 모듈을 가집니다. 복사한 저장소 하나가 곧 조직 하나입니다 |
| 사람 `Account` | Google 계정으로 로그인한 사람. 조직에 하나씩 있습니다. 이름, 이메일, 계정 상태, 조직 역할을 가집니다 |
| 팀 `Team` | 함께 일하는 단위. 업무와 기록은 모두 팀에 속합니다 |
| 멤버십 `Membership` | 사람이 어느 팀에 어떤 역할로 속하는지. 한 사람이 여러 멤버십을 가질 수 있습니다 |
| 직무 유형 `JobType` | 팀을 만들 때 고르는 기본값 묶음 (아래 "직무 유형") |
| 기능 모듈 `Module` | 켜고 끄는 기능 단위 ([README의 기능 구성](README.md#기능-구성-확정)) |

조직을 하나로 두더라도 조직 개념을 코드와 데이터에 분명히 둡니다. 조직 설정을 한곳에 모으고, 나중에 한 배포에 여러 조직을 담아야 할 때 바꿀 곳을 줄이기 위해서입니다. 다만 지금은 조직이 하나뿐이므로, 팀 소속 데이터에는 팀만 적고 조직을 따로 적지 않습니다.

## 사람과 역할

### 상태

| 대상 | 상태 | 뜻 |
| --- | --- | --- |
| 계정 | 활동 / 정지 | 정지되면 조직 전체에 로그인할 수 없음. 조직 관리자만 바꿈 |
| 멤버십 | 요청 / 활동 / 거절 / 정지 / 나감 | 팀 하나에 대한 상태. 정지는 그 팀에만 못 들어옴. 나감은 기록을 남긴 채 팀에서 빠짐 |

### 역할

| 역할 | 범위 | 할 수 있는 일 |
| --- | --- | --- |
| 조직 관리자 | 조직 전체 | 팀 만들기·보관, 직무 유형 관리, 조직에서 허용할 모듈 정하기, 시간대·휴일 달력, 로그인 허용 기준, 계정 정지, 조직 관리자 지정, 모든 팀의 관리 화면, 전체 활동 기록 |
| 팀 관리자 | 자기 팀 | 가입 승인·거절, 구성원 역할·정지·내보내기, 팀 설정, 팀 기능(허용된 모듈 안에서 켜고 끄기), 팀의 모든 업무 고치기, 팀 활동 기록 |
| 구성원 | 자기 팀 | 자기 업무 만들고 고치기(담당자는 자기만), 할 일, 리포트 공지 칸 쓰기, 공간 쓰기 |
| 읽기 전용 | 자기 팀 | 보기만 |

- 조직 역할(조직 관리자 여부)은 계정에, 팀 역할은 멤버십에 붙습니다. 둘은 따로입니다.
- 조직 관리자는 모든 팀에서 **팀 관리자와 같은 관리 권한**을 갖습니다. 다만 그 팀의 구성원은 아니므로 출석·EXP가 쌓이지 않고 공간에 들어가지 않습니다. 공간에 들어가려면 그 팀의 구성원이 되어야 합니다.
- 팀에는 활동 중인 팀 관리자가 한 명 이상 있어야 합니다. 마지막 팀 관리자는 내보내거나 역할을 낮출 수 없습니다. 조직 관리자도 한 명 이상 있어야 합니다.

## 들어오기와 가입

1. Google로 로그인합니다. 이메일이 조직의 로그인 허용 기준(예: 허용 도메인)에 맞지 않으면 들어올 수 없습니다.
2. 처음이면 계정이 만들어집니다. 계정만으로는 어느 팀도 볼 수 없습니다.
3. 팀 가입은 두 가지 길입니다.
   - 팀 관리자가 만든 **초대 링크**로 가입을 요청하고, 팀 관리자가 승인합니다.
   - 조직 관리자나 팀 관리자가 계정을 골라 **바로 추가**합니다(요청 없이 활동 상태).
4. 첫 조직 관리자는 배포할 때 환경 변수로 정한 이메일입니다. 그 이메일로 처음 로그인하면 조직 관리자가 됩니다. 이름은 로그인 설계 단계에서 정합니다.

## 직무 유형

팀을 만들 때 직무 유형을 고르면 아래 값이 팀에 **복사**됩니다. 복사한 뒤에는 팀 값이므로, 팀이 바꿔도 직무 유형은 그대로이고, 직무 유형을 바꿔도 이미 만든 팀은 그대로입니다.

| 직무 유형이 채우는 것 | 예 |
| --- | --- |
| 켤 모듈 | 개발 유형은 공간·퀘스트·칭찬 켬, 인증·만료일 관리 끔 |
| 업무 구분 라벨 | 팀이 업무를 나눌 때 쓰는 라벨 목록 (예: 기획, 개발, 검토) |
| 업무 추가 항목 | 업무에 더할 입력 칸 (예: 관련 링크) |
| 프로젝트 추가 항목 | 프로젝트에 더할 입력 칸 |
| 리포트 공지 칸 | 리포트 공지 칸의 제목 목록 |
| 리포트 주기 기본값 | 주의 시작 요일, 편집 마감 시각 |

- reberu는 일반적인 직무 유형 몇 개(예: 기본, 개발, 디자인, 운영)를 기본으로 넣습니다. 이름과 내용은 일반 단어만 씁니다.
- 조직 관리자는 직무 유형을 더하고 고칠 수 있습니다. 복사한 저장소는 자기 직무에 맞는 직무 유형을 조직 마이그레이션이나 조직 모듈로 더합니다.
- **고정 기능의 규칙은 직무 유형이 바꾸지 못합니다.** 업무 상태·우선순위, EXP·레벨 공식, 시즌 길이, 출석 규칙은 모든 팀이 같습니다.

## 모듈을 켜는 세 단계

```
설치됨 (코드에 있음) ──▶ 조직이 허용함 ──▶ 팀이 켬
```

| 단계 | 누가 | 뜻 |
| --- | --- | --- |
| 설치됨 | 개발자 | reberu 모듈과 복사한 저장소가 더한 조직 모듈. 코드와 마이그레이션이 들어 있음 |
| 조직이 허용함 | 조직 관리자 | 이 조직의 팀들이 켤 수 있는 모듈. 허용하지 않은 모듈은 팀 기능 화면에 나오지 않음 |
| 팀이 켬 | 팀 관리자 | 이 팀에서 실제로 쓰는 모듈 |

- 조직이 허용을 거두면 그 모듈을 켠 모든 팀에서 꺼집니다. 기록은 남습니다.
- 모듈 사이에 필요 관계가 있으면(예: 어떤 조직 모듈이 인증·만료일 관리를 넓혀 만든 경우) 필요한 모듈이 꺼질 때 함께 꺼지고, 켤 때 필요한 모듈을 먼저 켜라고 안내합니다.
- 모듈의 테이블은 켜고 끄는 것과 관계없이 마이그레이션으로 늘 만들어 둡니다. 켜고 끄는 것은 실행 중에 팀별로 정하는 값입니다.

### 모듈이 서버에 등록하는 것 (확장 지점)

모듈 하나는 아래를 한 묶음으로 서버에 알립니다. reberu 모듈과 조직 모듈이 같은 방식을 씁니다.

| 항목 | 내용 |
| --- | --- |
| 모듈 정보 | 이름, 설명, 기본 켜짐 여부, 필요한 모듈 |
| API | 이 모듈의 API. 꺼진 팀에서 부르면 없는 것처럼 응답 |
| 메뉴·화면 | 켜졌을 때 보일 메뉴 |
| 권한 | 이 모듈이 더하는 권한과 역할별 기본값 |
| EXP 출처 | 이 모듈이 주는 EXP 종류와 양 |
| 알림 종류 | 이 모듈이 만드는 알림 |
| 실시간 이벤트 | 개인·팀·공간 범위 중 어디로 보내는지 |
| 정해진 때 작업 | 매일 아침 만료 확인 같은 일. 이 모듈을 켠 팀에서만 돎 |
| 마이그레이션 위치 | reberu 모듈은 `db/migration/core`, 조직 모듈은 `db/migration/company` ([CONTRIBUTING.md 3절](../../CONTRIBUTING.md#3-업스트림-운영-규칙)) |

- 조직 모듈은 복사한 저장소의 자기 패키지에 이 묶음을 만들어 두기만 하면 서버가 찾아 등록합니다. 업스트림 파일은 고치지 않습니다.
- 구체적인 코드 모양(인터페이스, 패키지)은 도메인 모델 단계에서 정하고 [docs/ai/backend.md](../ai/backend.md)에 옮깁니다.

## 팀 데이터 나누기

### 무엇이 어디에 속하나

| 사람(계정)에 속함 | 팀에 속함 |
| --- | --- |
| 이름, 이메일, 기본 아바타, 계정 상태, 조직 역할, 알림 설정(D2), 방해 금지 시간 | 업무, 프로젝트, 오늘의 할 일, 오늘의 퀘스트, 리포트, 회의, 출석, EXP·레벨·시즌 기록, 업적, 칭찬, 알림, 활동 기록, 공간 위치, 휴식 기록, 산길 걸은 거리와 남긴 말, 아바타·책상 꾸미기, 팀 설정, 켠 모듈 |

- 알림은 팀에 속합니다. 위쪽 막대의 알림은 지금 보는 팀의 것만 보여 주고, A3 팀 고르기에서 팀마다 안 읽은 수를 보여 줍니다.
- 꾸미기는 팀별 레벨로 열리므로 팀마다 따로입니다.
- 한 팀에서 다른 팀으로 기록을 옮기지 않습니다. 팀을 옮기면 새 팀에서 레벨 1부터 시작합니다.

### 서버가 지키는 규칙

1. **팀 데이터 API는 주소에 팀이 들어갑니다.** 예: `/api/teams/{teamId}/tasks`. 어느 팀의 데이터인지 늘 분명하게 합니다.
2. **요청마다 서버가 멤버십을 확인합니다.** 사용자가 보낸 팀 번호를 믿지 않고, 로그인한 사람이 그 팀의 활동 멤버이거나 조직 관리자인지 확인한 뒤 "지금 팀"을 정합니다. 역할과 모듈 켜짐도 이때 함께 확인합니다.
3. **팀 데이터는 늘 팀과 함께 찾습니다.** "번호로 업무 찾기"가 아니라 "이 팀의 이 번호 업무 찾기"로만 찾습니다. 다른 팀 업무의 번호를 알아도 꺼낼 수 없습니다.
4. **다른 팀 데이터는 없는 것처럼 응답합니다.** 권한 없음이 아니라 "찾을 수 없음"으로 응답해 다른 팀에 그런 데이터가 있는지조차 알 수 없게 합니다.
5. **팀을 넘는 참조를 막습니다.** 업무의 프로젝트, 담당자, 팀 회의 참석자는 모두 같은 팀의 것이어야 합니다. 저장할 때 확인합니다. 여러 팀 사람이 함께하는 것은 조직 데이터(공용 회의, 연회장 모임)로만 합니다.
6. **실시간도 같은 규칙입니다.** 팀·공간 범위를 들을 때 멤버십을 확인하고, 팀을 바꾸면 이전 팀 범위는 그만 듣습니다([05-realtime.md](05-realtime.md)).
7. **정해진 때 작업은 팀마다 따로 돕니다.** 마감 알림, 시즌 마감 같은 작업은 팀 단위로 나눠 처리하고, 한 팀이 실패해도 다른 팀은 계속합니다.

### 검증 방법

- 팀 두 개(예: "바다팀", "숲팀")와 두 팀에 모두 속한 사람, 한 팀에만 속한 사람으로 테스트 데이터를 만듭니다.
- 모든 팀 데이터 API에 대해 "다른 팀 사람이 부르면 찾을 수 없음"을 테스트합니다.
- 역할별(조직 관리자, 팀 관리자, 구성원, 읽기 전용) 권한 표대로 되는지 테스트합니다.
- 꺼진 모듈의 API를 부르면 찾을 수 없음이 되는지 테스트합니다.

## 조직 소속 데이터

대부분의 데이터는 팀에 속하지만, 조직 공간 모듈의 데이터는 어느 팀에도 속하지 않고 **조직에 속합니다.** 팀 데이터 분리 원칙은 그대로이며, 조직 데이터는 팀 데이터를 참조하지 않습니다.

| 조직에 속함 | 누가 보나 |
| --- | --- |
| 조직 설정, 시간대, 휴일 달력, 직무 유형, 허용 모듈 | 조직 관리자 (휴일 달력은 모두가 결과만 봄) |
| 연회장 모임 (일정, 안건, 질문, 요약) | 조직의 활동 계정 모두 |
| 공용 회의 (참석자, 안건, 메모, 결과) | 그 회의 참석자와 조직 관리자 |
| 조직 공간 위치 | 서버 메모리에만 둠 |
| 조직 활동 기록 | 조직 관리자 |

### 조직 단위 모듈

조직 공간처럼 팀이 아니라 조직 전체에 하나만 있는 모듈은 **조직 단위 모듈**입니다.

- 켜는 단계가 둘입니다: 설치됨 → 조직이 켬(F4). 팀 기능 화면(E6)에는 나오지 않습니다.
- 확장 지점은 팀 단위 모듈과 같고, 모듈 정보에 "조직 단위"라고 적습니다. 조직 모듈(복사한 저장소)도 조직 단위로 만들 수 있습니다.

### 조직 데이터에 대한 서버 규칙

1. 조직 데이터 API는 주소에 팀이 없습니다. 예: `/api/org/assemblies`. 팀 데이터 API와 주소로 구분합니다.
2. 요청마다 활동 계정인지 확인하고, 공용 회의는 참석자이거나 조직 관리자인지 확인합니다.
3. 공용 회의 참석자는 여러 팀에서 고를 수 있지만, 회의 기록은 팀 데이터(업무, 프로젝트)를 가리키지 않습니다. 회의에서 나온 할 일은 각자 자기 팀 API로 업무를 만듭니다.
4. 조직 공간에서 보이는 다른 팀 사람의 정보는 계정 정보(이름, 기본 아바타, 상태)와 팀 이름뿐입니다. 레벨, EXP, 칭찬처럼 팀에 속한 기록은 보이지 않습니다.

## 팀 설정과 고정 규칙

| 팀마다 다를 수 있음 (팀 설정) | 모든 팀이 같음 (고정) |
| --- | --- |
| 팀 이름, 직무 유형(만들 때), 켠 모듈, 업무 구분 라벨, 업무·프로젝트 추가 항목, 리포트 공지 칸, 리포트 주의 시작 요일·마감 시각, 공간 정원 | 업무 상태와 우선순위, 업무 권한 규칙, EXP 출처별 기본값과 레벨 공식, 시즌 길이, 출석 기록 규칙과 근무일(조직의 시간대·휴일 달력), 역할 종류 |

## 팀의 생애

| 일 | 처리 |
| --- | --- |
| 만들기 | 조직 관리자가 이름, 직무 유형, 첫 팀 관리자를 정해 만듦 |
| 보관 | 조직 관리자가 보관. 구성원이 더 들어올 수 없고 모든 화면이 보기만 됨. 기록은 남음 |
| 복원 | 조직 관리자가 복원 |
| 지우기 | 하지 않습니다. 기록을 남기기 위해 보관만 둡니다 |

## 활동 기록

- 팀 안의 변경(업무, 구성원, 팀 설정, 팀 기능)은 팀 활동 기록에 남고, 팀 관리자가 E5에서 봅니다.
- 조직 변경(팀 만들기·보관, 직무 유형, 허용 모듈, 계정 정지, 조직 관리자 지정)은 조직 활동 기록에 남고, 조직 관리자가 F6에서 봅니다. 조직 관리자는 모든 팀의 활동 기록도 봅니다.
